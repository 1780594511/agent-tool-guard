# 用于理解代码和准备面试

先读 `tests/test_gateway.py` 的审批成功、失败回滚、并发消费三个测试，再读 `Gateway.invoke`。它们把安全要求转成“数据库到底多了什么”的断言。

| 模块/入口 | 输入 | 输出 | 设计原因 |
|---|---|---|---|
| `auth.py::authenticate` | 原始 opaque session token，可选 CSRF | 服务端 `Principal` | 身份查数据库，模型/前端传来的角色不参与授权 |
| `schemas.py::TOOL_SCHEMAS` | 工具名和 JSON 参数 | 严格、规范化参数，或校验错误 | 防止额外字段、类型混淆、未知工具进入执行层 |
| `policy.py::authorize` | 当前 Principal、已校验参数、当前策略 | 授权资源及版本，或拒绝码 | RBAC 只给角色能力；具体 grants 防同部门横向越权 |
| `gateway.py::Gateway.invoke` | 会话 + ToolRequest | succeeded / denied / pending_approval / failed，原因、关联 ID | 唯一确定性执行入口；串联幂等、审批、复核、事务 |
| `gateway.py::decide` | 审批人会话、审批 ID、动作 | 新审批状态 | 审批不等于业务执行，不允许自批，不扩大原权限 |
| `executor.py::_execute` | 事务连接 + 后端私有 permit | 业务结果标识 | 封闭工具集合，不执行动态代码、命令、路径或任意 URL |
| `db.py::audit` | 结构化事件 | append-only 条目及哈希链接 | 复盘建议、决策和实际效果；不存正文减少日志泄漏 |
| `models.py::ModelAdapter.next` | 任务、此前工具结果、超时 | Tool proposals / 文本 | 模型接入不改变授权代码；真实/Mock 共用网关 |
| `agent.py::run_task` | 已验证会话、任务、provider、请求键 | 任务及调用轨迹 | 步数/超时限制，任务幂等，失败不直接放行 |
| `evaluation.py::oracle` | 实际业务快照、案例预期 | 完成、越权、误拦截、失败证据 | 判断真实状态，不相信模型说“已经完成” |

## 1. 为什么不能只加一句安全提示词？

提示词影响模型是否提出危险建议，但无法作为可信授权条件。文档、用户任务和模型输出都可能出错。这里即使 Mock 已被恶意文档诱导，仍由后端对 `hr-001` 检查实际会话权限。安全提示词可以辅助，不能成为数据库访问控制。

## 2. RBAC 和 ABAC 在哪里？

RBAC：策略中 `roles.engineer.classifications` 允许研发分类。资源级属性：具体文档分类、版本、`grants(user_id, document_id)` 以及当前操作与目的地。研发用户有 `rd-001` 授权不等于能读取 `rd-002`。审批人的 scopes 是另一条权限轴。

## 3. 规范化、摘要和审批是什么关系？

调用参数必须先通过 schema，再根据工具语义规范化。`["rd-001", "pub-001"]` 和反序的文档集合等价；目的地则精确匹配，不做模糊推断。摘要绑定完整上下文，用于发现变化。摘要不能代替重新鉴权，也不是加密。

审批到执行之间可能发生 ACL 撤销、策略变更、文档更新或审批人权限撤销。执行时重新读取这些状态，避免只检查一个 `approved=true`。

## 4. 为什么是一个数据库事务？

如果先把审批标为已消费，后创建导出，后者失败会留下“审批没了、业务没成功”。如果先导出后消费，两个线程可能同时通过检查。v0.1 用 `BEGIN IMMEDIATE` 串行化，再在 SAVEPOINT 中写副作用、消费审批及审计，提交或回滚一起发生。

面试中要主动解释限制：真实邮件、HTTP 下游不属于 SQLite 事务；不能声称将本地原子提交直接推广为分布式 exactly-once。扩展需要 transactional outbox、唯一 operation ID、下游幂等和对账。

## 5. 幂等键不是审批凭据

幂等键只声明“这是同一次业务请求的重试”。键作用域为当前用户，必须绑定相同参数。已有成功结果可以重放，但要重新检查当前读取权限。审批已消费后不能用新键再执行一次。

任务也有独立 request_key，避免网络重发让整个 Agent 重新创建工单。重放只返回已有任务，不重新调模型。

## 6. 什么叫执行隔离？

实际隔离包括：模型适配层没有执行器引用；HTTP 没有执行器路由；封闭的三种 SQL 工具；合成数据专用数据库；A/B 只在标记为 evaluation 的独立数据库和子进程中运行。没有运行模型生成的 Python/JS。

不要说私有函数名或 `_Permit` 能抵抗已经在后端运行任意代码的攻击者。真正 OS/container sandbox、网络出口和密钥隔离属于后续部署工作。

## 7. 审计能证明什么？

调用提案、授权原因、审批动作、执行复核、最终结果均有 call/task ID。成功执行审计与业务写入在同一事务，因而不会出现“记录成功但副作用回滚”的正常流程错误。哈希链能发现普通条目被改动，但掌握数据库文件的攻击者可以重算整条链。需要独立审计服务才有更强保证。

文档正文只从业务表按当前权限取回；审计不保存模型全文或敏感正文。日志中的 ticket title/body 只保存长度和哈希。

## 8. 如何解释评测结果？

Mock 不是 LLM。A 和 C 使用相同的故意易受文档诱导的规则模拟器，B 增加两条显式恶意标记的模拟识别规则。比较证明的是网关在已知调用序列上的权限与事务行为，不是现实模型攻击成功率。协议探针是确定性安全测试，应与模型行为分开报告。

正常完成率只统计任务的业务目标达到与否；还单独记录正常案例中的策略违规，避免把“导出了”误当成“安全导出了”。真实模型模式需记录模型标识、样本数量、重复次数和原始失败，未运行就写“未测”。

## 自己练习修改

1. 给 engineer 增加 `rd-002` grant，观察同一个请求由拒绝变为允许；然后撤销，验证历史正文不再返回。
2. 申请导出并批准，用 admin 提升资源版本，再以发起人执行，观察绑定失效。
3. 在测试中让 `_execute` 写入后抛异常，确认 inbox 为 0、审批仍为 approved；恢复后同键重试只导出一次。
4. 在评测 JSON 添加案例及业务预期，运行开发集，确保 oracle 能识别一条真实副作用，而不是只检验 status 字符串。
